# AIFriend

Android 端「AI 好友 / AI 智能体团队」应用：用户创建带角色设定的 AI 好友，选择模型，与它多轮对话，并在首页统一管理。另有聊天室、云端朗读，以及一套由客户端规则引擎驱动的 AI 狼人杀。

当前版本 **0.0.91**（`versionCode = 91`）。

  - 狼王：夜里照常下刀，白天被票出可以开枪；最后一枪若打穿屠边，狼队即使全灭也能翻盘

  - **三档提示词风格**：引导式（默认，规则 + 板子 + 身份打法 + 狼队战术全给）、自由式（规则与技能照给，打法交给模型）、搜索式（只给版型与胜负，规则打法让模型自己查或联网查）。详见[提示词风格](#提示词风格)
  - **联网搜索**：搜索式 + 厂商支持时，发言和决策请求会带厂商自己的联网字段（豆包 / 千问 / 混元 / 智谱四家）；DeepSeek、Kimi 的对话接口没有内置搜索，会静默退化成「极简提示词但不联网」
  - **跨天公开台账**：发言原文只喂今天 + 昨天，所以「谁跳过预言家、报了什么验人、说投 A 却投了 B」由 `PublicLedger` 从公开发言里摘出来跨天累积，第 3 天以后模型才不会凭印象编
  - **每轮记录板**：本轮的发言顺序（`3-4-5-6-7-8-1-2` 这种连排）与「谁已经说过、谁还没说」由 `RoundBoard` 直接摆给模型，模型不用再猜谁还没开口、自己排在第几个
  - 发言逐字上屏（流式），深度思考模型的思维链可折叠展开；夜里单人行动的发言不流出来，思考过程只在观战视角可见（参与的局听不到别人的心里话）
  - **夜里顶栏不报「谁在做什么」**：参与局的夜里那一行只写「夜间进行中」，不写「守卫守护」「女巫用药」，更不写「狼人商议 1/3」（那等于把狼的数量报给全场）；只有本人正处在那一阶段时才给阶段名
  - **流式显示不等朗读**：已经开口的人不再被朗读状态掐断（以前一条发言里闸门会反复开关，屏幕上就是「说到一半突然消失」）；还没吐字的人仍等喇叭空闲，防剧透的初衷保留
  - **token 用量**：每次请求的入 / 出 token 逐条记录，思考中先按已生成的字数估算（标「约」），落地后被真值覆盖；复盘页有按座位的汇总卡
  - 每一步都有思考时限（快速 / 标准 / 宽松 / 不限，可开局选、可局中改）：超时按兜底继续并关掉那个座位本局的深度思考，思考气泡上带实时秒表，对局设置里能看到每个人最近/平均用时和超时次数
  - 自动朗读：每人一个音色，好友自己配过的优先，没配的按座位自动分互不相同的内置音色（八个人同一个声音会分不清谁在说）
  - 详细规则见 [AI 狼人杀](#ai-狼人杀) 一节

## 对话协议

所有厂商共用 `core:ai/entity/OpenAICompatibleAI.kt`：请求体为 `{ model, messages: [{role, content}], stream }`，回复取 `choices[0].message.content`；差异只在 `ApiConfig` 和模型列表解析。`Friend.systemPrompt` 把「昵称 + 角色 + 详细设定」拼成 `system` 消息放在历史之前。

## 联网搜索

开关是 `IAI.webSearch`（`chat` / `chatStream` / `chatWithUsage` / `decide` 四个方法都有），**默认 false**；厂商是否支持由 `supportsWebSearch` 声明，**默认 false，没验证过的一律不声明**。目前只有狼人杀的「搜索式」会把它打开（`WerewolfDirector.webSearchFor`），且要求同时满足「选了搜索式」和「这家厂商支持」。

| 厂商 | 字段 | 备注 |
| --- | --- | --- |
| 豆包（方舟） | `web_search_options: {}` | 空对象即开。**不能和 `tools` 同传**——方舟文档写明两者同时出现时以自定义工具为准，搜索被静默关掉 |
| 通义千问 | `enable_search: true` | 千问不支持 `web_search_options`，会提示改用 `enable_search` |
| 混元 | `enable_web_search: true` | 收到千问那个字段会直接 400 |
| 智谱 | `tools: [{type:"web_search", web_search:{enable:true, search_result:true}}]` | `search_result` 必须开，否则回复里不带引用，事后查不出到底搜没搜 |
| DeepSeek | — | 对话接口没有内置搜索，只有独立的 `/tools/search`，要自己编排工具循环 |
| Kimi | — | `$web_search` 已于 2026-10 下线，改独立 REST 接口，同样要自己编排 |

- **不支持的厂商一个字节都不加**：`OpenAICompatibleAI.buildRequest` 里是 `applyWebSearch(webSearch && supportsWebSearch)`。传了反而更糟——提示词里写着「你可以联网查」，模型会把记忆当成查证结果
- **重试包装必须透传**：`RetryableAI` 漏传 `webSearch` 等于开关被吃掉，测试里专门有一条守这个
- **正常路径每一条发言、每一次决策都带搜索**。摘除只发生在「请求被服务端拒掉」之后，那是失败恢复，不是默认降级
- **联网和 `response_format: json_object` 会打架**：部分厂商要先跑一轮工具轮，JSON 约束在那一轮不保证生效。撞上时两条路径（流式降级回一次性、`decide` 的非超时异常）会摘掉搜索重试一次——**仅当错误看起来是搜索冲突**（消息里点名 search / tool，或 400 / 422 参数拒绝）；429 限流、5xx、断网一律不摘，因为摘了照样失败，还白丢一次检索
- 代价只有时间：一次检索通常多二三十秒，抓回来的网页内容也计入输入 token。所以搜索式是慢档——提示词里写的是「该查就查」，不是「可以查也可以不查」

## 聊天室

房间把多个好友放在一起，用户发一条消息，默认由房间内所有 AI 各自回答。

**定向 @**：在输入框里输入 `@` 会弹出成员选择器，选中后插入 `@名字`，并把成员 ID 一起存进这条消息。**被 @ 的成员才回答，这一轮对其他成员不可见**；没选 @ 时全员可见。成员改名/删除不会影响历史消息的可见性。

**停止生成**：每个「正在输入…」右侧有「停止」，顶栏在有人生成时也会出现「停止」按钮，用于一次取消全部；取消只丢弃本次请求，不会写入消息。

**房间设置**：顶栏齿轮进入设置页，可改房间名、填写「房间设定」（会拼在每位成员的 system prompt 前面，例如「你们是一个评审团，先各自给结论」），以及管理成员。点「保存」写入并退回聊天页；**有改动还没保存时按返回会先弹确认**（保存并返回 / 放弃修改），避免改了半天一按返回全丢。

**讨论模式（窗口互见）**：设置里可开启，其他 AI 的发言只保留最近 **1–5 轮**（按用户消息划分轮次），以「（某成员 的发言）」的 user 消息注入。开启讨论模式、以及调大回看窗口时都会弹窗提示 token 会同步上涨。讨论模式下每位 AI 的上下文预算从 6000 降到 **4000**，窗口越大，其他人的发言占用的额度越多。

**顺序发言**：发言顺序一律由**客户端随机决定并串行**——每位成员依次说完，后一位能看到前一位的回复，因此是有来有回的讨论，而不是各答各的。随机顺序在每次发送时独立抽取，不是固定的轮转，也不是「谁先返回谁先说」。

**自由对话**：房间设置里的开关，**必须先开启讨论模式**（关闭讨论模式时该开关置灰，且关闭讨论模式会一并关掉自由对话）。开启后，用户每发一条消息，成员先按随机顺序各答一次，然后继续按「一次接话 = 一轮」自动互聊，直到用完「接话次数」（1–20，默认 3）。最后一轮会主动收口，或在某位成员在回复里带上 `[END]` / `【结束】` 收尾标记时提前结束。

- 节奏：串行发言的每一次（首批的第二位起、以及每一次接话）都会先停 **1.2s + 随机 0–1.8s** 再发请求，避免上一条刚上屏下一条立刻顶上来、看起来像机器人刷屏。
- 下一位发言人：解析上一条回复里的 `@名字` 作为交接（取最后一个 @，按最长名字匹配）；没解析到就从「除自己以外」的成员里随机挑，不会出现同一个人连着说两句。
- 话题锚点：自由对话最容易「越聊越散」的根因不是模型不行，而是**它看不到话题本身**——上下文按 token 预算从最新往回裁，几轮之后用户最初那句需求就被裁掉了，成员只能盯着上一句猜主题。所以每次接话都会把「最近一条该成员可见的用户发言」抽出来，作为独立一行提示追加在**最后**（因而不受裁剪影响），并明确要求「紧扣这个话题、不要另起新话题」。用户一句话没说时退回用房间设定当锚点。实现在 `feature/room/data/RoomTopic.kt`。
- 收口：自由对话的**最后一轮**（即接话次数用完的那一轮）会换成收口提示——要求给出结论、不再提新问题、并在末尾带上 `【结束】`。收口位置跟用户设置的接话次数走，**不写死第几轮**：设 3 就在第 3 轮收，设 6 就在第 6 轮收，这样「接话次数」才真的说了算（`AutoChatPolicy.isFinalTurn`）。
- token 控制：自由对话每一轮的上下文预算单独压到 **2000**，并且**每条别人的发言都单独算一轮**（`burstAsRounds`），所以回看窗口 N 真的等于「最近 N 条别人的发言」，不会因为一轮里堆满消息而窗口失效。自由对话内部会把窗口兜底到 **2 轮**（`AUTO_CHAT_MIN_WINDOW`）：只看 1 轮等于只看到紧挨着的那一句，话题会像传话游戏一样越传越偏；设置页在窗口为 1 时会提示这一点。
- 打断：自由对话期间用户再发消息，会先取消整条自动对话链再按新消息重新开始；顶栏显示「自由对话中 3/6」和「结束」按钮，停止会取消整个循环（不是只停当前那一个请求）。
- 容错：某位成员请求失败会换下一位继续，**失败的这次不算接话次数**；连续失败 2 次才整体停下，避免把次数全烧在报错上。收尾标记只用于判断结束，会从气泡文本里去掉。
- 不做滚动摘要：更早的讨论按窗口和预算自然滚出上下文，不额外花 token 维护纪要。话题连贯性靠上面的锚点保证，而不是靠保留全部历史。

**清空聊天记录**：房间设置页底部的「危险操作」，显示当前消息条数，二次确认后删除本房间的全部消息；房间、成员、讨论设置都会保留。清空时同时把成员的 `joinSeq` 重置为 0，避免清空后新消息被旧的加入位置过滤。正在进行的请求会被取消。

> 取舍：窗口互见只解决「其他人发言」的膨胀；自己的历史仍受 4000 token 预算约束。再往后如果要长期讨论，需要上「滚动摘要」（共享纪要 + 最近消息窗口）。

**上下文策略（方案 B）**：每个 AI 只看到「房间内所有用户消息 + 它自己的历史回复」，看不到其他 AI 的回复，避免互相污染。实现是 `buildRoomContext(messages, friendId)` 一次过滤，以后要升级成「共享全文（方案 C）」只需改这一处。

- 发送：用户消息先落库并显示，然后按客户端随机出的顺序**串行**请求每位成员，每完成一位就立刻上屏
- 分页：打开房间只加载最近 50 条，滚到顶部自动补更早的 50 条；分页不影响 AI 上下文，上下文仍按 token 预算截断
- 并发：开启自由对话时「房间 + AI」仍各有一把 `Mutex`，加上整条链是串行的，同一 AI 不会被打断，上下文不会串
- 状态：每个 AI 独立的「正在输入」和错误提示，失败只影响它自己，可单独重试
- UI：单列时间流，用户消息右对齐、AI 回复左对齐并署名；每条消息带 HH:mm，跨天自动插入「今天 / 昨天 / 日期」分割；长按气泡可复制或引用（引用会把「发送者 + 摘录」插到输入框开头）；顶部「成员」弹窗显示角色/模型、移除需二次确认、最多 6 位
- 房间列表：置顶优先，其余按创建时间；首页长按房间可置顶/取消置顶/删除；创建房间支持按昵称 / 角色 / 模型搜索
- 搜索：首页搜索框同时过滤聊天室名；房间顶栏放大镜搜索已加载消息，点结果跳到对应消息
- 导出：房间设置页「导出聊天记录」会读取整屋消息生成 Markdown，通过系统分享面板发送
- 房间头像：设置页点头像选图并裁剪，首页房间卡片和房间顶栏都会显示
- 房间模板：新建房间提供「评审团 / 头脑风暴 / 角色扮演」，点一下填入房间设定
- Token 估算：设置页显示「本轮约 N 次请求、单个 AI 上下文约 X tokens」，按字符估算，仅作参考
- 系统消息：创建房间、「X 加入了聊天室」「X 退出了聊天室」会插入灰色居中的系统提示；这些通知会以「（聊天室通知）」前缀作为 user 消息同步给房间内的 AI，保证它们知道人员变化（不用 system 角色是为了兼容只允许首条 system 的厂商，如 Moonshot）
- 新成员：`Room.memberJoinSeq` 记录每个成员的加入位置，新加入的 AI 只看得到加入之后的消息，不会同步历史；加入时会自动发一条自我介绍式问候（创建房间时不自动打招呼）
- 持久化：房间、成员、消息都在 Room 的 `rooms` / `room_members` / `room_messages` 表（库当前 `version = 10`），`rooms` 表保存房间设定 `prompt`、讨论开关 `discussionEnabled`、回看窗口 `discussionWindow`、自由对话开关 `autoChatEnabled`、接话次数 `autoChatTurns`、置顶 `pinned`、头像 `avatarPath`；`room_messages` 保存定向 @ 的成员 `targetIds`。旧的 `sequentialSpeaking` 列已废弃，保留列以兼容历史库，代码不再读写
- 消息 `seq` 在应用启动时会从历史最大值继续（`seqCounter` 种子），避免重启后新消息的 seq 小于成员 `joinSeq`，导致新成员看不到新消息
- 已有消息在成员被移除后仍保留，界面上会显示「已移除」

## 云端朗读（TTS）

朗读是独立于对话的一条链路：凭证在设置页单独填（`tts_*`），不和对话 Key 共用，可以只配对话不配朗读，也可以反过来。

| 服务      | 协议                                                           | 备注                                                                                                                                              |
| ------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| MiniMax | `POST {baseUrl}/t2a_v2`                                      | 非流式 JSON，`data.audio` 是 hex 编码 mp3                                                                                                              |
| 科大讯飞    | `wss://tts-api.xfyun.cn/v2/tts`                              | WS 流式，HMAC-SHA256 签名；必须 `aue=raw`（`lame` 分片各自带 LAME 头，会让 MediaPlayer 反复重置出「叽里咕噜」）                                                               |
| 火山引擎    | `POST {baseUrl}/api/v3/tts/unidirectional`                   | HTTP Chunked 多帧 JSON，按 `{}` 层级切帧（不能按行读）；旧 v1 不支持 2.0 音色；鉴权两套头——旧控制台 `X-Api-App-Id` + `X-Api-Access-Key`，新控制台 `X-Api-Key`，先按一种试、被拒（401/403）再换另一种 |
| 阿里百炼    | `POST {baseUrl}/api/v1/services/audio/tts/SpeechSynthesizer` | 返回音频 URL，再下载                                                                                                                                    |
| 腾讯云     | `POST tts.tencentcloudapi.com`                               | TC3-HMAC-SHA256 签名，`Response.Audio` 是 base64                                                                                                    |

- 音色是**角色属性**（`Friend.voiceId`），不是全局设置：设置页只管凭证和「真合成一句」验证，挑音色在建角色页的音色面板里
- 面板按 女声 / 男声 / 童声 / 方言 / 其他 分组（方言优先于性别），可搜索，每个音色都能当场试听；内置列表只放官方文档能查到的 ID，并留了**手填 ID** 兜住克隆音色、国际站音色和需单独开通的精品音色
- **朗读前必须清洗文本**（`SpeechText.forSpeech`）：去掉旁白、markdown 标记、emoji、重复标点，补句末标点；清完没有字母数字就整条跳过
- 失败文案统一走 `TTSReadableError.of(t, provider)`，把「Key 错了」「音色没开通」「网络断了」分开说，而不是把原始异常抛给用户


## 厂商额度

点开好友详情页有一块「服务商额度」，显示这个好友用的那家厂商还剩多少。

**不用网页登录**：各家开放平台都有 OAuth，但个人开发者申请 OAuth 应用要企业资质、要审核、要配回调域名，周期以周计，App 里还得塞 WebView 和 token 刷新。而余量这件事，八成厂商直接开了 HTTP 接口，用设置页已经填好的那把 Key 就能查。

| 厂商 | 接口 | 鉴权 | 显示 |
| --- | --- | --- | --- |
| DeepSeek | `GET api.deepseek.com/user/balance` | Bearer | 总余额 / 赠金 / 充值 |
| Kimi | `GET api.moonshot.cn/v1/users/me/balance` | Bearer | 可用 / 代金券 / 现金 |
| MiniMax | `GET api.minimaxi.com/v1/token_plan/remains` | Bearer | 5 小时窗口 / 本周剩余 |
| 智谱 | `GET open.bigmodel.cn/api/monitor/usage/quota/limit` | 裸 Key | 5 小时 / 本周 / 月度 |
| 硅基流动 | `GET api.siliconflow.cn/v1/user/info` | Bearer | 余额 / 充值 / 已用 |
| OpenRouter | `GET openrouter.ai/api/v1/credits` | Bearer | 总额 − 已用 |
| 火山方舟 | `POST ark.cn-beijing.volcengineapi.com/?Action=ListModelActivations` | **AK/SK 签名** | 模型开通状态 |
| 阿里百炼 | — | — | 没开放余额接口 |

- **火山方舟是唯一的例外**：它的管控面接口不认聊天用的 API Key，只认 Access Key ID + Secret Access Key，所以设置页给豆包这一栏多两个输入框。查到的还不是钱，是**模型开通状态**——方舟的模型要在控制台单独开通，没开通调用直接 404，而 `GET /models` 会把没开通的也列出来，于是好友建好了、看着也正常，一开口就说不了话
- **智谱的额度接口不认 `Bearer ` 前缀**，带了就 401，但它别的接口又只认 Bearer。所以鉴权写法配成候选列表依次试，第一个不报 401 的算成功，多发一次请求换掉一次赌博
- **MiniMax 的 `*_usage_count` 名字骗人**：它返回的是**剩余**次数（已用 = 总量 − 它）；`*_remaining_percent` 已经是剩余百分比，别再减 100
- **智谱的 `percentage` 是已用比例**不是剩余；`number` 是周期长度（5 小时 / 1 周 / 1 个月）不是额度总量，拿它去除 `remaining` 会算出 10000%
- **MiniMax 的业务失败照样 HTTP 200**，得看 `base_resp.status_code`；只判状态码会把「套餐没买」显示成「剩余 0%」
- **SHA-256 / HMAC 是手写的**：Android 单元测试跑在 mockable android.jar 上，那份 jar 里 `javax.crypto.Mac` 是抛异常的桩——用 JDK 实现的话签名逻辑在单元测试里根本跑不起来，只能靠手点一次真机验证。正确性由 FIPS 180-4 与 RFC 4231 的标准向量钉住
- 「这家没有公开接口」和「这次没查成」在界面上分开说：前者是产品事实（百炼就没开放），后者换个 Key 或重试可能就好了


## AI 狼人杀

一局游戏由 `feature:werewolf` 的规则引擎驱动，AI 只负责「说话」和「做决定」（人类座位由你亲自说、亲自投），规则判定与隐私隔离全在客户端。

### 板子

| 板子          | 身份构成                  | 特点                    |
| ----------- | --------------------- | --------------------- |
| 6 人快局       | 2 狼 + 预言家 / 女巫 + 2 民  | 屠边，狼人打穿任意一边即赢，两边各只需两刀 |
| 8 人标准局      | 2 狼 + 预女猎 + 3 民       | 默认板子，容错高              |
| 9 人标准局      | 3 狼 + 预女猎 + 3 民       | 3 狼票权 3:6，必须拆票才推得动人   |
| 10 人守卫局     | 3 狼 + 预女猎守 + 3 民      | 民只有 3 个，打民边比打神边快      |
| 10 人狼王局     | 狼王 + 2 狼 + 预女猎守 + 3 民 | 狼王被票出的那一枪可能直接打穿屠边翻盘   |
| 12 人守卫局（警长） | 4 狼 + 预女猎守 + 4 民      | 4 狼已接近绑票线，警徽归属决定白天节奏  |
| 12 人白痴局（警长） | 4 狼 + 预女猎白 + 4 民      | 白痴挡一次放逐，好人多一次试错       |
| 12 人熊局（警长）  | 4 狼 + 预女猎白熊 + 3 民     | 熊每天给一条公开线索，好人按邻座推     |

### 规则要点

- **第 1 天先上警竞选 + 警长投票，再公布昨夜死讯**——否则等于给死者一张选票
- 遗言只有三种人：首夜死者、每次被票出者、任何原因出局的警长（第 2 夜起夜里死的不再发言）
- **被猎人枪带走的人不留遗言，但警徽照样要处理**——遗言和警徽是两条独立规则
- 守卫守 + 女巫救 = 死（守救同归），会写给全场；守卫不能连守
- 票出白痴不死、只是失去票权；狼王只有被票出能开枪
- **退水的人首轮没有警长票**（上过警的人本来就不投），但**平票 PK 那一轮照样能投**——「退了就永远没票」是常见误解，两个阶段票权不同
- **单爆顺延、双爆吞警徽**：竞选被自爆打断，警徽只是推到下一个白天，连续两次才作废。竞选发言和 PK 发言被爆**各记一次**，不分阶段。自爆的狼当晚仍在狼队里，定刀结束才真正离场
- 狼刀可以落在队友、自己身上，也可以空刀（`wolfVotes` 的值可为 `null`）；夜里被刀还能开枪的只有猎人，狼王不行
- 白天串行发言（后一位能看到前一位），投票 / 狼刀 / 上警并发求解

### 开局流程

配置分两页，**开局按钮只在第二页**：

- 第一页「组局」：怎么玩、板子、「我的身份」、选人。底部是「下一步 · AI 设置」，不会直接开局
- 第二页「AI 设置」：连接自检、提示词风格、牌手风格、思考时限、发言长度、朗读。底部「开局」才是真的开局

**连接自检按当前打法验**。选搜索式时，探活请求本身也会带上联网开关（`IAI.probe(webSearch = true)`）：厂商没有内置搜索就当场判不合格，**一个字节都不发**，红字直接写在自检卡上，开局按钮变「忽略问题，仍然开局」。切到第二页、或换打法都会自动重测——前提变了，旧绿灯不算数（`ApiCheck.webSearch` 记着这条结论是在哪个前提下测的），但同一前提、十分钟内的通过结果照旧复用，不会反复花检索的钱。

**联网能力是静态的，第一页选人时就标出来**：好友行下会写「没有联网搜索能力，搜索式下只能凭记忆答」。不用等自检跑完，也不用花一次请求——DeepSeek、Kimi 这类没有内置搜索的厂商，选人那一刻就能看见。

搜索式的探活超时也单独放宽到 45 秒（`SEARCH_PROBE_TIMEOUT_MS`）：检索要先去搜、再塞回上下文，沿用 20 秒会把所有支持联网的厂商都判成超时。

失败分两种，界面分开说：**连不上**（去查 Key、查网络）和**没有联网搜索能力**（换厂商，或改用引导式/自由式）。后者不会把牌桌卡住，但模型会拿记忆当查证结果——所以自检卡会写「换厂商，或者改用引导式/自由式」，而不是让人反复点重试。

### 提示词风格

开局在配置页选，三档（`WerewolfPromptStyle`）。原则是「**规则是事实，打法才是答案**」：

| 风格 | 给什么 | 砍掉什么 | 单次 system（12 人守卫局实测） |
| --- | --- | --- | --- |
| 引导式（默认） | 规则 + 板子 + 身份打法 + 读人框架 + 狼队战术菜单 | — | 狼 9.3k / 神 5.8k / 民 5.5k token |
| 自由式 | 规则 + 板子 + 术语 + 私有信息 | 所有打法：读人框架、板型结论、战术菜单、藏身诱导、残局挡刀 | 约 3.0–3.3k |
| 搜索式 | 只有版型 + 胜负（含警长 1.5 票、按票权算） | 连规则细节也不给，交给模型自己回忆或联网查 | 约 0.8k |

- 自由式砍的只是**打法**，事实照给：本局有几条不是标准局先验（屠边、警长 1.5 票、守救同归、自爆当晚仍定刀），不给就会拿网上记忆去推，推出来的结论整个是错的
- 搜索式是唯一的例外，它把这些也交给模型，**属于实验档**；选它会自动把思考时限抬到「宽松」（一次超时会把那个座位整局的深度思考关掉，第一局就会全员变傻）
- 搜索式下只要厂商支持联网，**发言和决策请求都会带搜索开关**。唯一不联网的是「要不要当场自爆」那一步：它是 8 秒硬超时的是非题，检索必然超时，加上去等于把这个功能关掉
- 厂商能力不够时**不再静默退化**：DeepSeek、Kimi 的对话接口没有内置搜索，选搜索式会在第二页的自检里被判红、拦在开局之前，而不是等打到一半才发现「写着会查、一次没查」
- 三档共有的底线不能砍：身份、狼队友、验人记录、本轮任务与输出格式——砍了就打不完这一局

内容本身仍分三层，缺一层 AI 就会「弱智」（搜索式只保留与第一层等价的「版型 + 胜负」）：

- `ruleBrief`：这局按什么规则判定
- `boardBrief`：这张板子几狼几神几民、打哪边省刀、容错几次
- `strategyBrief`：这个身份该用什么方法判断

**跨天台账**（`engine/PublicLedger.kt`）：发言原文只喂今天 + 昨天（`EXPANDED_DAYS = 2`，另有 3200 字预算），所以到第 3 天，第 1 天谁跳的预言家、报了什么验人、谁说了投 A 却投了 B，在上下文里一个字都不剩。台账把这些**可核对的事实**从公开发言里摘出来跨天累积：

- 摘三样：自称身份、报出的验人、每天「说投谁 / 实际投谁」。谁真谁假仍然交给模型
- 只读 `audience == null` 的公开发言和公开唱票卡；夜聊与内心活动一律不进，否则等于泄底
- 「如果我是预言家」这类假设句不算声称；取当天**最后**一个票向，前面带否定的（「别投 3 号」）跳过
- 拼在【当前局势】之后、私有简报之前——同一类材料挨着放，模型才会拿它当推理依据

**每轮记录板**（`engine/RoundBoard.kt`）：发言顺序和发言进度本来是编排层的内部安排，模型看不到，只能猜。猜错一次就是「把还没开口的人当成已经表过态」（替别人发言）、「不知道自己排在第几个」（说「等 5 号说完我再补充」这种空话）、「把上一轮说过的话当这一轮的」（重复背书）。这块板子把这些**本轮事实**直接摆出来：

- 一块板子装两样东西，不拆成两段提示词：**本轮发言顺序**（`3-4-5-6-7-8-1-2` 这种连排）和**谁已经说过 / 谁还没说**；末尾再补一句「你是几号、本轮第几个发言」
- 顺序是**引擎里的唯一一份**（`WerewolfGame.currentRoundSpeakers`）：编排层照它叫人，提示词照它告诉模型。狼队商议的「头狼先、其余按座位」原来写在编排层，现已下沉到 `WerewolfGame.nightWolfSpeechOrder`——两份各写一遍必然走偏（模型说自己第二个说，牌桌上他排第五个）
- 只覆盖四种逐座位发言的阶段（白天讨论 / 竞选发言 / 遗言 / 狼人商议）；投票、夜晚行动这类没有发言顺序的阶段**不输出**，硬凑一个只会让模型以为自己该说话
- 警长还没选方向时顺序尚不存在，**整块不输出**：此时 `discussionOrder` 只是默认值，写进去等于骗模型
- 阶段或轮次一变（狼刀平票重谈、警长 PK）旧名单自动作废，不会把上一轮的成绩带过来
- **狼人商议只对狼人可见**，好人拿到的是空串而不是被裁剪过的版本——狼队有几个人、谁先指挥是夜里才揭晓的信息，白天拿到就是泄底
- 拼在【公开台账】之后、私有简报之前，与台账同属「可核对的事实」

**昨夜判断回看**（`WerewolfDirector.ownNightBrief`）：白天的上下文只喂公开消息，原本会把本人夜里已经想通的结论一起滤掉。出现过这样的割裂：女巫夜里毒 10 号时已经推出「2 号翻牌猎人 → 1 号假预言家 → 4 号真」，白天发言时却又站回 1 号、把票砸给真预言家。现在白天的正文里会单独带一段【你昨夜的判断】：

- 只捞**本人**的 `NIGHT_ACT`（守卫守谁、预言家验谁、女巫用药的结论与依据）——按 audience 过滤后再卡 seat，狼队夜聊是 `WOLF_CHAT`，走 `wolfPlan` 那条私有通道，不会混进来
- 只回看最近两夜，每条截 120 字，避免陈年判断挤占预算；没有夜间记录就不输出，不占位
- 明确提醒「别在白天直接说出来，尤其别报身份、别报你验到了谁」——夜里知道谁是狼是私有信息，白天只能拿它修正自己的站边和票
- 这是不增加模型调用次数的修复：只多几百字输入，堵的是「夜里想通、白天照错」这条昼夜割裂

引导式提示词里的读人框架（`prompt/ReadingTells.kt`）补了两条本局教训：**硬反证（翻牌 / 开枪）出现就必须重盘站边**，不能拿「对方说话难听、警徽流改口」抵消；**被查杀的人怎么回应是验真假的关键**——真被冤的人第一反应是证明自己，不是反手拉人下水。同时夜间决策请求（`includeReading = false`）不再带那一大段「从发言读人」框架——下刀、查验、用药时没有发言可读，带着只是白烧几千字输入；白天发言与投票照旧带，默认行为不变。

源码按「身份 + 板子」两层组织，因为**板子只是身份的集合**——按板子写守卫规则要抄三遍：

```
prompt/
  rules/GameRules.kt        所有人共用的规则（胜负、绑票、投票、遗言、自爆）
  roles/XxxKit.kt           一个身份一个 Kit：机制 / 白天打法 / 私有简报 / 收尾叮嘱
  boards/XxxBoard.kt        一张板子一个 Board：人数结构 + 狼边打法
  tasks/TaskBriefs.kt       按阶段：这一步要做什么
  WerewolfPrompt.kt         只做拼装
```

- 打板子按**规则**认，不按 key：`Boards.of(config)` 比对身份构成 + 有无警长 + 胜负规则，三样全中才算同一张板子；对不上（自定义局）返回空文案，绝不把别张板子的结论套上去
- 狼下刀单独有一段 `wolfKillBrief`，把「规则」翻译成「用法」：撞守等于这一夜白过；昨夜刀口没死说明守住了或救了 → 今晚连刀；刀死了说明守卫今晚会守最该守又没守过的位 → 该往外置位动刀。它只吃公开信息（昨夜刀口 + 实际出局名单），**绝不读守卫守了谁**
- **提示词微调**（设置页「提示词微调」）：分「全局」和「当前板子专属」两栏，两段拼起来加在每位 AI 的 system prompt **最末**，因此优先级高于内置打法。它只影响 AI 怎么打，不进公共播报、不进 transcript，信息隔离不受影响
- 续档时按存档里的 `config` 反查板子 key（`WerewolfBoards.keyOf`），所以「暂停 → 继续」不会丢掉板子那栏的设定；已开局的对局要暂停再继续才会用上新改的内容
- 落档时把当时生效的那段提示词写进快照（`TableSnapshot.customPrompt`），复盘页和导出文件里都能看到这一局是按什么设定打的

### 思考过程与作弊边界

深度思考模型的思维链会以**浮动漫画框**挂在本人头像旁，边想边长：

- 观战局和已结束的局恒开，且不给开关
- 参与的局默认关闭——看到别人的思考等于读心，「猜谁在想什么」就变成了主玩法；要打开就顶栏点「思考」胶囊，同时会常驻一条提醒自己是在作弊
- 开关只放行「想的内容」，**不放行「谁在动」**：夜里的行动者高亮照样遮住，泄露身份比作弊更严重
- 决策类请求（投票、狼刀、上警）也有思维链：`StructuredChat.decide` 带 `onReasoning` 回调时走流式，攒齐正文再解析 JSON；并发阶段用占位锁保证同一时刻只有一个气泡在长

### 参与局的可见性

参与局（人类在桌上）和观战局共用一套界面，但**能看见什么**差得很远。这套判断集中在 `WerewolfLiveMapping.toLive` 一处，三处（座位高亮、牌桌底部的「正在思考」、流式发言气泡）必须同源——分开写迟早有一处漏判，而漏判的后果是把身份摊在桌上。

- **夜里除了本人，谁都不留下痕迹**：守卫守护、狼人商议、狼人下刀、预言家查验、女巫用药五个阶段，参与局里既不亮座位也不出气泡。**狼人下刀也算夜里**——它虽然是并发阶段、没有唯一的「当前是谁」，但正在下刀的那几个人就是全部狼人，气泡一冒出来狼就全亮了
- **顶栏副标题也要按视角收**：夜里那一行原来写的是 `stageText`（「狼人商议 1/3」），把**阶段名**和**人数**一起报了出来——「守卫守护」「女巫用药」是在报这个角色在场，「1/3」是把狼的数量直接送给全场，平民扫一眼就知道这局有几匹狼。现在参与局的夜里只给一句中性的「夜间进行中」；只有**本人正处在这一阶段**时才给阶段名（他本来就知道自己是什么角色，而且需要知道自己正卡在用药 / 下刀这样的环节里）；观战是上帝视角，阶段名和进度照给
- **夜里的超时提示不能点名**：「5 号的决定超出 60 秒」等于当着全场的面报身份——夜里的「决定」只有守卫 / 预言家 / 女巫 / 狼人做。参与局的夜里，超时的不是本人就只说「刚才有一步超出时限，已按兜底继续」，不给座位、不给名字、不给「发言 / 决定」；本人和观战照旧点名
- **对局设置面板里的按座位数据也是侧信道**：夜里超时会让那个座位的「超时 N 次」和「深度思考被关」变样，顶栏的脱敏提示已经让参与者知道「刚才有人超时」，面板再写清楚是谁，两处一对就把夜间角色锁死了。所以参与局面板里，这两项一律不显示按座位的版本（超时次数只给顶部的总数，耗时只给**白天**那本账）；观战和已结束是上帝视角，照实显示
  - 引擎侧把「被关思考」拆成两份：玩家手动关的 / 夜里超时自动关的。引擎照样照关（不然那个卡死的模型会一直卡），但参与局的界面上只有手动那份能露出来
- **狼人密谈只对狼队开放**：本人是狼时看得见队友的密谈；本人是好人时一个字都看不到
- **身份只随公开走**：`roleLabel` 和「是不是狼」都等到身份公开才有资格给（观战 / 结束 / 翻过牌的白痴）。参与中的局里，界面连「谁是狼」这个布尔值都拿不到——想从客户端泄露身份没有路径
- **夜里死因要模糊**：被刀、被毒都只显示「夜」；放逐和自爆照实显示（那是公开信息）
- 夜里唯一还亮着的是**本人**：轮到自己守人、查验、用药时，自己的座位该亮还是要亮
- **私有信息必须真的到得了本人眼前**：预言家的查验结论写在引擎那条私有消息里（「查验 3 号：狼人」），牌桌上单列一档排版（青绿、正常字号、「仅你可见」），不跟投票念头共用那套压暗小字。预言家本人还有一条常驻的**验人本**（`selfChecks`），白天报验人时一眼就有，不用翻记录流
  - 这一条曾经整个是空的：引擎只写「查验 N 号」加一句理由，谁是狼一个字都不说。AI 预言家能从提示词的 `seerChecks` 里读到结果，**人类预言家没有提示词**——他只能看牌桌，于是查完人什么都不知道，等于这个身份废了
  - 结论只落在 `audience = {预言家}` 的那条消息里：上下文那边 `transcriptFor(seat)` 按 audience 过滤，公共局势只读 `history`，台账只收 `audience == null` 的发言——好人的提示词里一个字都看不到
  - 复盘那一节原本是拿 `seerChecks` 反查补结论的（「查验 2 号 → 狼人」）。消息正文里有了结论，反查就只在**老存档**上补，新版不重复拼
- **查验结论长在座位上**：结论不只躺在记录流和验人本里，还直接挂在**被验的那个座位**头像下面（`seerVerdict`）——牌桌里那枚身份徽标位，平时只有上帝视角才填得出东西（身份名），现在对局中给预言家本人挂「好人 / 狼人」。白天报验人、对账全靠这一眼，不用翻记录流去对座位号
  - 这一格只给**参与局里的预言家本人**：好人和狼人拿到的都是 null（那是他的私有情报，别人看见了等于把局势直接交出去）。上帝视角和已结束的局也不给——那里所有人的身份本来就摊开着，这一格留给身份名，「好人 / 狼人」是多余的信息
  - 徽标位的优先级是**查验结论 > 出局原因 > 身份名**。结论排第一是因为它是预言家唯一的价值所在，且只有他一个人看得见
  - 配色跟验人本一致：**狼人是红**（狼人杀里「红 = 狼」是既有约定），**好人是青绿**；夜里青绿提一档（`SeerTealNight`），深底上才看得清

### 思考时限

模型没有时间概念，不设上限就会一直想下去。实测有座位连想十几分钟，最后给出的还是很差的答案——它不报错也不中断，牌桌就那么停着，用户分不清是 AI 在深思还是这局已经死了。传输层那 8 分钟 / 30 分钟的超时是兜底，不是节奏控制。

- 四档：**快速**（思考 30s）、**标准**（60s，默认）、**宽松**（120s）、**不限**（只受网络超时约束）；发言段不限——AI 说话即吐 token，流挂住由传输层兜底
- 开局在配置页选，开局后点牌桌右上角齿轮随时改，改完立刻对下一个请求生效；档位随存档走，续档不会悄悄回到默认
- **超时之后**：决策走兜底动作（投票弃权 / 查验挑候选 / 狼刀挑好人），发言保留已经说出的半句（一个字都没说就给一句「我这轮先听大家的」），牌桌上提示一句并说明后果
- 同时**本局关掉这个座位的深度思考**：超时的头号原因就是思考把额度吃光了，继续让它边想边等只会一步比一步慢。这条也进存档——续档后不会把已经关掉的座位又打开
- 面板里能看到每个人的账本：最近一步耗时、平均耗时、本局超时次数，以及手动开关深度思考（只能关，角色本来没开的点不开，那是好友自己的属性）
- 思考气泡右上角有实时秒表（`12s / 60s`），快到上限变红；上限区分决策与发言，不会拿一个数去套另一个
- 人类座位不受时限约束：轮到你想多久是你自己的事

**「不限」档位的两个坑**

- 这一档思考段和发言段的时限都是 0，导演里的看门狗**不启动**，超时只由传输层喊。传输层的静默上限（5 分钟）会被「模型一直在吐思考内容」绕过去——socket 不静默——真正兜底的是 30 分钟总时长
  - 这一支以前和「标准」档的超时**结果不一样**：标准档由看门狗掐，落一句空话、牌局继续；不限档走传输层，正文一个字没吐时把异常抛出去，**整局停在「模型响应超时」上**，续档还会重放同一阶段、再撞一次同一个超时。现在两条路统一成同一个结果
- 思考量会随天数膨胀：上下文一天比一天长，深度思考模型的思考长度跟着涨（实测第 1 天狼聊几百字，第 3 天能到几万字）。「不限」档位恰好是最容易撞上这个坑的——它把唯一的自动刹车（思考超时后关掉那个座位的深度思考）也一起关掉了
- 碰上了先在牌桌右上角齿轮里把档位降一档、关掉那个座位的深度思考，再按返回键（这一步会存档），然后「接着打」——续档会带着新设置回来

### 复盘

- 复盘演出按**时间线重新构建画面**，绝不读终局状态——直接画终局就是开场一地尸体、警徽挂在最后那个人身上。出局名单、警徽归属、谁能看见哪句话，都跟着事件逐条推进
- 支持上一条 / 播放暂停 / 下一条 / 倍速；不朗读时按字数给阅读时间
- 局内好友被删也能复盘：进入前逐个座位挑一个替身（或静音），替身复用原来的座位音色
- 导出分两种：**Markdown**（给人读，不可反解）和 **`.wwg` 对局文件**（给 App 读，导入后还能重演一遍）。导入永不覆盖已有对局，撞 id 会另存一份

### 存档

对局存在独立的 `werewolf.db`，权威是 `werewolf_games.snapshot` 一列（整局快照，含 transcript），快照有版本号（当前 v23），旧档自动升级。改状态字段必须升版本并写兼容解码。没有消息表——会话本身就是快照的一部分，拆表只会制造两个真相。

请求参数（`customPrompt`、`turnLimit`、`thinkingOff`）也写在快照里，但**不进 `WerewolfTable`**：它们是「这一局怎么跑的」，不是「牌桌现在是什么样」，混进局面会让复盘和导出都被迫背上它们。读档时用 `decodePrompt` / `decodePacing` 单独取。

**续档时人不在了也能接着打。** 存档的座位表存的是好友 id，而这一局可能是昨天开的——中间好友被删了、账号换了、设备没同步，那个 id 就查无此人。这类座位**连探活都做不了**（没有资料就没有模型可测），以前是被 `mapNotNull` 悄悄丢掉的，一路走到建座位才炸成一句「找不到小咪的资料」——那句话没有出口，用户想换人都没地方换，这一局就成了打不开的死档。现在这类座位和「连不上」的座位一起进换人面板：

- 两种坏法**分开说**：「好友已经不在了」（只能换人，换 Key 也没用）和「连不上」（Key 过期、模型下线，也许换个 Key 就能开打）。混成一句「席位有问题」，用户会先去折腾 Key，折腾完发现还是不行
- 换人只改 id / 名字 / 模型三个字段：座位号、身份、死活、死亡原因、天数、历史全部保留——换人不是重开
- 候选池排除本局在座的所有好友：同一个好友顶两个座位，牌桌会出现两个同名同模型的人，AI 互相称呼时就乱了

## 自定义头像

- 入口：创建好友页选择头像；创建完成后在 1:1 对话页点头像可更换；首页右上角头像用于设置用户自己的头像
- 选图：系统 Photo Picker（`ActivityResultContracts.PickVisualMedia`），不需要存储权限
- 裁剪：选图后进入 `UIAvatarCropDialog`，双指缩放、拖动选择范围，带三分线辅助构图，确认后才输出正方形 JPEG
- 处理：`AvatarStore` 把裁剪结果缩放到 256×256 存到 `files/avatars/<id>_<时间戳>.jpg`，并清理同 id 的旧文件
- 展示：`UIAvatar` 统一组件，有图片显示图片，没有就显示名字首字 + 按名字稳定的配色
- 持久化：好友头像路径存在 `StoredFriend.avatarPath`，用户头像路径存在 `user_avatar_v1`

## 删除智能体

入口：首页好友列表**长按好友** → 「删除好友」→ 二次确认（对话页右上角原来的垃圾桶已移除）。

一次删除会清理：

- 好友本身和它的完整会话历史（`Friend.messages`），之后不会再作为上下文发送给模型
- 所有聊天室里的成员关系与 `memberJoinSeq`
- 它在聊天室发过的所有消息（避免残留内容和上下文）
- 头像文件 `files/avatars/<id>_*.jpg`
- 正在进行的请求结果会被丢弃（返回时校验好友是否还存在）
- 如果它在某个房间，会追加一条系统提示「X 已被删除并移出聊天室」

## 删除聊天室

入口：首页「聊天室」卡片**长按** → 二次确认。

删除会同时清掉 Room 里的 `rooms` / `room_members`（外键级联）/ `room_messages`，不可恢复。

> 关于「模型侧的上下文」：本项目的调用是**无状态**的——每次请求都把历史消息随请求发送，没有使用厂商的 thread / session / `previous_response_id`。因此删除本地历史后，这些内容不会再发给模型；厂商是否保留请求日志由各厂商政策决定，chat completions 接口没有提供删除接口。

## 上下文预算

每次请求前会用 `trimToBudget()` 截断发给模型的历史（`core/ai/model/ContextBudget.kt`，1:1、聊天室、狼人杀共用一套规则）：

- 从最新消息往回保留，默认预算 **6000 估算 token**，至少保留 **6 条**，保证最后一轮完整
- 只影响请求内容，本地展示和持久化的历史不受影响
- 估算规则：CJK 字符按 1 字符 ≈ 1 token，其它字符按 4 字符 ≈ 1 token（不引入各厂商 tokenizer）
- 聊天室先按「加入位置 + 方案 B」构建上下文，再统一截断
- 这样单轮输入成本有上界，不会随对话长度无限增长

## 数据持久化

存储已从 DataStore 迁移到 **Room（SQLite）**，数据库文件 `aifriend.db`。

- 实现位置：`core/repository/.../storage/db/`
  - `friends` / `friend_messages`（外键级联删除）
  - `rooms` / `room_members`（联合主键，记录 `joinSeq`）/ `room_messages`
  - `profile`（用户头像路径）
- 写入：增量写，不再是整包 JSON 快照
  - 加好友 / 改头像：`upsert` 或单字段更新
  - 消息：逐条 `insert`（自增 id 保证顺序）
  - 删除好友：级联删除会话消息，同时清理房间成员和它在房间里的消息
- 读取：ViewModel 初始化时通过 `FriendRepository` / `RoomRepository` 加载
- 迁移：首次启动 `LegacyMigration` 会把旧 DataStore 的 `friends_v1` / `rooms_v1` / `room_messages_v1` / `user_avatar_v1` 一次性导入 Room，成功后清掉旧 key；DataStore 现在只用于这次迁移
- 版本：`aifriend.db` 当前 `version = 10`（v1 → v10 全部有 `Migration`）；狼人杀用独立的 `werewolf.db`（`version = 2`），对局存 `werewolf_games.snapshot` 一列整局快照，不建消息表
- 偏好类数据（各厂商 Key、TTS 凭证、狼人杀设置与提示词微调）仍在 DataStore，不进 Room：它们不属于任何一条业务记录

> 构建用 KSP 做 Room 注解处理（`ksp = 2.3.6`，匹配 AGP 9 内置 Kotlin）。AGP 9 默认禁止 KSP 通过 `kotlin.sourceSets` 注入生成目录，`gradle.properties` 里用 `android.disallowKotlinSourceSets=false` 放行。
